## Publication plan

This stage did not publish, create or push tags, create a GitHub Release,
commit, push, open a pull request, or rerun GitHub Actions.

After an authorized release-branch commit and green Quality/A1/E2E on that
exact versioned SHA:

1. Re-run `pnpm release:check`, `pnpm test:mcp:all`, `pnpm mcp:check`, the
   three-runtime tarball matrix, and registry existence checks.
2. Confirm all ten candidate versions are absent and `latest` remains 3.2.2
   for existing packages.
3. Use the approved publisher to run
   `pnpm exec changeset publish --no-git-tag`. Do not add `--tag rc` while in
   pre mode; Changesets rejects a custom tag in pre mode and derives `rc` from
   `.changeset/pre.json`.
4. Verify all ten packages exist at 4.0.0-rc.0 under `rc`; verify existing
   packages still have `latest` at 3.2.2. `@openapi-to/mcp` is currently a new
   package and has no `latest`.
5. Create the conventional per-package Git tags
   `<package-name>@4.0.0-rc.0` only after all registry publishes succeed, then
   push the reviewed tags.
6. Create a prerelease GitHub Release from the aggregate tag and these release
   notes.
7. Install `openapi-to@rc` and `@openapi-to/mcp@rc` in clean consumers and
   repeat the three binaries, 3/8/10 Tool matrices, and Prepare/Apply smoke.

Changesets 2.28.1 does not treat `changeset publish --help` as a read-only help
command. It starts registry discovery and must not be used for a rehearsal.
During this preparation it was interrupted during `npm info`, before any
`npm publish`; all ten candidate version endpoints were then independently
verified as HTTP 404.

## Rollback plan

- Before publish: stop, leave registry and tags unchanged, fix the release
  branch with an appropriately scoped changeset, and regenerate the candidate.
- Partial publish: inventory exact registry versions first. If the reviewed
  artifacts remain valid, publish only the missing fixed-group packages;
  otherwise deprecate the published subset with a clear RC message and prepare
  a new candidate. Never overwrite a published version.
- RC bug: deprecate the faulty RC, add a patch changeset for the fix, let
  Changesets calculate the next prerelease, and repeat every gate. Before an
  `rc.1` publish, explicitly verify the dist-tag plan for the new MCP package;
  Changesets' `only-pre` behavior must not move it to `latest`.
- Dist-tag error: restore each existing package's `latest` to 3.2.2, point
  `rc` at the approved candidate, and verify clean installs. Dist-tag repair
  changes pointers only; it does not delete immutable package versions.
